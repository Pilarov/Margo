## 1. Как это будет работать (одним сценарием)

Представь разработчика, который поменял логику поиска (например, Этап 4 — ADR-007) и хочет знать: **стало лучше или хуже?**

1. У него поднят сервер: Postgres + `pnpm dev:server` (порт 3000).
2. В базе засеяны тестовые «рабочие памяти» на одного пользователя (seed).
3. Он запускает **одну команду**:
   ```
   pnpm --filter @retaindb/server bench
   ```
4. Скрипт (black-box, ходит по HTTP):
   - проверяет, что сервер жив (`GET /health`);
   - берёт 21 контрольный вопрос из `qa/qa-set.json`;
   - на каждый вопрос делает `POST /v1/memory/search` (как это делал бы агент);
   - сравнивает id найденных памятей с эталонными (slug → id из `qa/memory_map.json`);
   - считает recall@10 (+ precision/MRR/NDCG);
   - сравнивает с сохранённым эталоном `qa/baseline-<date>.json`;
   - печатает таблицу и пишет отчёт `reviews/BENCH-<date>.md`;
   - завершается кодом `0` (всё ок) или `1` (регресс).
5. Разработчик видит:
   ```
   recall@10   0.937   baseline 0.937   Δ 0.0pp    PASS
   precision@10 0.42   baseline 0.42    Δ 0.0pp    PASS
   p99_ms       138    baseline 131     Δ +5.3%    PASS
   → GATE: PASS
   ```
   или:
   ```
   recall@10   0.900   baseline 0.937   Δ -3.7pp   FAIL (порог -2.0pp)
   → GATE: FAIL
   ```

**Суть**: это **чёрный ящик по HTTP**. Бенчмарк не залезает внутрь кода — он дёргает тот же API, что и реальный клиент, и проверяет наблюдаемое качество. Поэтому он ловит регресс независимо от того, как ты рефакторил внутри.

## 4. Что я буду делать по шагам (нарратив)

### Шаг 1. Починю user-mismatch (без него замеры врут)
**Сейчас**: `qa/qa-set.json` говорит, что пользователь — `working-memory-test-user`, а сидер (`seed-dialectic-data.py:22`) создаёт данные для `dialectic-test-user`. Retrieval-eval берёт user из `memory_map.json` (верно), а synthesis-eval — из `qa-set.json` (неверно) → **спрашивает профиль пустого пользователя**, отсюда разброс 0.53–0.87.
**Сделаю**: объявлю `qa-set.json` источником истины; сидер и оба eval будут читать user оттуда. Пересею данные.
**Результат**: synthesis-eval впервые меряет реального пользователя.
**ADR**: предусловие к ADR-010 §2.

### Шаг 2. Вынесу метрики в функции
**Сейчас**: `eval-retrieval.py` умеет только recall.
**Сделаю**: добавлю `recall/precision/MRR/NDCG` как чистые функции с self-тестом на известных числах.
**Зачем**: gate должен сравнивать метрики; одна метрика недостаточна.
**ADR-010 §1.**

### Шаг 3. Соберу runner
**Сделаю**: `scripts/benchmark/run.py` — один вход, который делает healthcheck → seed(опц.) → прогон вопросов → метрики → отчёт. Старый `eval-retrieval.py` останется тонкой обёрткой (или удалю).
**Зачем**: сейчас каждый скрипт запускается руками отдельно, нет единого результата.
**ADR-010 §3, §5.**

### Шаг 4. Зафиксирую baseline и gate
**Сделаю**: команда `bench:baseline` сохраняет текущие метрики в `qa/baseline-<date>.json`. Обычный прогон сравнивает с ним и падает, если качество упало больше порога.
**Зачем**: это и есть защита, ради которой весь этап. Без baseline «стало хуже» неотличимо от «и так было».
**ADR-010 §4.**

### Шаг 5. Заменю хрупкую synthesis-метрику на LLM-judge
**Сейчас**: проверяем, что в ответе диалектики встречаются подстроки-анкоры. «Friday» ≠ «Fridays», переформулировка не засчитывается → нестабильно.
**Сделаю**: функцию `judgeAnswer()` на сервере (LLM сравнивает смысл ответа с эталоном, `temperature=0`), новый LLM-task `judge`, endpoint `POST /v1/admin/benchmark/judge`. Python-скрипт зовёт этот endpoint (не дублирует ключи).
**Зачем**: метрика должна отражать смысл, а не совпадение слов.
**ADR-010 §7; общий код с live answer-quality (ADR-011 §2).**

### Шаг 6. Добавлю latency- и cost-замеры
**Сделаю**: latency — прогон фиксированных запросов с warmup и повторами, p50/p95/p99. Cost — число LLM-вызовов/токенов.
**Честно**: latency на пуле 100k требует данных, которых может не быть → на Этапе 1 мерю на текущем пуле, 100k откладываю. Cost требует учёта usage от LLM — если его нет, это отдельная мелкая задача инструментирования; предлагаю решить сейчас (см. §6).
**ADR-010 §1, §2.**

### Шаг 7. Добавлю воронку потерь (drop-off)
**Сейчас**: `searchMemories` отдаёт наружу только тайминги (`MemorySearchDiagnostics`), но не видно, **сколько кандидатов отсеялось на каждом шаге**.
**Сделаю**: добавлю counts в диагностику (vector → type-recall → candidate pool → rerank → final), подпишусь коллектором в `api/memory.ts:691`, отдам через `GET /v1/admin/telemetry/drop-off`.
**Зачем**: когда recall просел, нужно видеть — это vector не нашёл, или отсеял scope/rerank.
**ADR-011 §1; питает ADR-007.**

### Шаг 8. Соберу TelemetryCollector
**Сделаю**: агрегатор (средние, перцентили, retention по слоям) с size-cap, без I/O в горячем пути, без содержимого памятей/запросов (приватность).
**Зачем**: единая точка вместо разрозненных модулей (ADR-011 Context).
**ADR-011 §1, §6.**

### Шаг 9. Конфиг, тесты, калибровка
**Сделаю**: секции `benchmark`/`telemetry` в конфиге (env > json > default); unit-тесты (judge, collector, funnel, config); прогоню и откалибрую пороги gate.
**ADR-010 §6; ADR-011 §7.**

## 6. Принятые решения (утверждено)

1. **Cost** — инструментировать учёт токенов **сейчас**. ✅ `llm-client.ts` оборачивает `chat.completions.create` и шлёт `usage` в collector.
2. **Latency-пул** — данных нет, **придумать генератор**. ✅ `scripts/benchmark/gen_pool.py` (N синтетических памятей, seeded) + `qa/latency-set.json`.
3. **Baseline** — **в git** (`qa/baseline-<date>.json` + `qa/baseline.json`).
4. **Judge** — **reuse** task `dialectic` (`getLLMClient(llmCfg.dialectic)`).
5. **Drop-off** — **динамические стадии**. Телеметрия/QC — отдельный механизм: `MemorySearchDiagnostics.stages` — массив именованных стадий (retrieval владеет словарём), collector группирует по имени. При переходе на S0–S3 (ADR-007) телеметрия не меняется.

## 8. Прогон на живом сервере — результаты

**Инфраструктура**: Postgres :5432, Margo :3000 (`pnpm exec tsx`, `setsid`), embedding local.

| метрика | значение |
|---|---|
| recall@10 | **0.937** |
| precision@10 | 0.138 |
| MRR | 0.674 |
| NDCG@10 | 0.709 |

**Latency** (balanced, cache off, 21 запрос): p50 **35ms**, p95 **48ms**, p99 **49ms** (SLO 220ms — с запасом).

**Drop-off** (21 запрос): `vector` retention 1.00 → `type_recall` 1.075 → `graph_temporal` 1.00 → **`intent_rerank` 0.306** → `final` 1.00. Главная потеря — intent_rerank (32.7 → 10).

**Gate**: PASS (повторный прогон vs baseline).

### Найденные баги (исправлены в `1232fcb`)

1. **auth**: `isAdmin` никогда не выставлялся → все `/v1/admin/*` возвращали 403 (включая существующий `/v1/admin/latency/*`). Исправлено: OSS single-tenant → владелец ключа = admin.
2. **`memory.ts:635`**: `profile` имел `.default("fast")`, который перекрывал `fast_mode:false` → benchmark мерил fast mode. Исправлено: убран default.
3. **`memory.ts:757`**: `diagnostics.fast_mode` перезаписывался на `true` при lexical fallback → телеметрия врала. Исправлено.
4. **seed**: прогон сразу после seed давал recall 0 (async embedding). Исправлено: `wait_until_indexed`.
5. **кэш** искажал замеры (hit rate 1.0). Добавлен `MEMORY_SEARCH_DISABLE_CACHE`.

### Остаётся

- **Известные gap**: `q-package-manager` = 0.00 (pnpm), `q-backend` = 0.67 (grpc-comms) — semantic-gap, цель ADR-007.
- **Judge e2e** не проверен (нужен LLM API key).
- **Latency на пулах 10k/100k** — `gen_pool.py` готов, прогон не делали.
- **Калибровка порогов gate** — на одном baseline; нужны серия прогонов.
- **Дубликаты памятей** в seed (semver/deploy-fridays дважды) — возможно, от повторных seed-запусков; проверить.
